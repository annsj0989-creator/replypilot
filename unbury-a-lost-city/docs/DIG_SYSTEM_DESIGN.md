# 발굴 시스템 기술 설계 (PHASE 0)

UNBURY A LOST CITY! — 발굴 시스템의 방식 비교, 선택 근거, 구조.

---

## 1. 평가 기준

사양서 3장 기준으로 다음 순서로 평가했습니다.

1. **발굴 감각**: 조준한 곳이 점진적으로 파이는가? 깊이감이 있는가? 반응이 즉각적인가?
2. **시각 품질**: 회색 블록이 아니라 실제 모래처럼 보이는가?
3. **모바일 성능**: 저사양 기기에서 30FPS 이상을 지킬 수 있는가?
4. **서버 권한**: 상태를 서버가 소유하고 검증할 수 있는가? 다른 플레이어에게 자동으로 보이는가?
5. **저장**: 발굴 상태를 작게 저장하고 정확히 복원할 수 있는가?
6. **구현·유지 복잡도와 위험**

## 2. 후보 비교

| 기준 | A. 높이맵 + Roblox Terrain 복셀 **(채택)** | B. Part 기둥 격자 | C. EditableMesh 변형 메시 |
|---|---|---|---|
| 모습 | 매끄러운 모래 표면, 경사·구덩이가 자연스러움. Sand/Sandstone 재질과 엔진 조명 그대로 사용 | 계단식 블록(마인크래프트풍). 매끄럽게 하려면 웨지 조합 필요 | 가장 자유로움(정점 색, 임의 해상도) |
| 해상도 | 수평 4스터드(복셀 크기), 수직은 점유율로 연속값 | 원하는 대로(2스터드면 64×64 구역에 1,024개 Part) | 원하는 대로 |
| 충돌 / 걸어서 들어가기 | 엔진이 자동 생성. 구덩이 안으로 걸어 들어갈 수 있음 | Part 충돌 그대로 | **변경마다 충돌 재생성(CreateMeshPartAsync) 필요** — 비동기·고비용. 별도 충돌 프록시가 필요 |
| 멀티플레이 복제 | 서버가 쓴 지형이 자동 복제 | Part 속성 변경 복제(많으면 트래픽 증가) | 복제 안 됨 — 각 클라이언트가 같은 메시를 다시 만들어야 함 |
| 모바일 비용 | 지형 메싱은 엔진 최적화 영역, 변경 영역만 다시 메싱 | 구역당 수백~천여 개 Part, 구역 수만큼 증가 | 메시 메모리 예산이 기기별로 다르고 초과 시 생성 실패 가능 |
| 서버 권한 | 높이맵을 서버가 소유 → 지형은 높이맵에서만 생성 | 동일하게 가능 | 시각은 클라이언트, 판정은 서버 — 두 표현이 어긋날 위험 |
| 저장 | 칸당 1글자(16×16 구역 = 256자) | 동일 | 동일 |
| 구현 복잡도 | 낮음~중간 | 낮음 | 높음 |
| 주요 위험 | 4스터드 해상도가 거칠게 보일 수 있음(→ 실기 확인 필요) | 비주얼이 사양서의 "자연스러운 모래"와 맞지 않음, Part 수 증가 | 충돌·메모리·게시 요건 등 플랫폼 제약이 많음 |

**제외:** 입자/물리 모래 시뮬레이션 — 사양서에서 금지(성능 검증 없는 대규모 물리).

### 선택: A. 서버 높이맵 + Terrain 복셀 쓰기

- 사양서의 "자연스럽고 만족스러운 발굴"과 "구덩이 안으로 들어가는 깊이감"을 엔진 기능으로 바로 얻을 수 있습니다.
- 표시되는 지형은 **오직 높이맵에서만** 만들어지므로 "발굴 진행 상황과 시각적 상태가 항상 일치" 요구를 구조적으로 보장합니다.
- 다른 플레이어에게 자동으로 보입니다(후속 공동 발굴의 기반).
- C(EditableMesh)는 PHASE 2에서 **시각 전용 레이어**(예: 발굴 가장자리 디테일)로 재평가할 수 있지만, 판정·충돌의 기반으로는 쓰지 않습니다.

## 3. 구조

```
[클라이언트]                                   [서버]
DigController                                 DigService
  마우스/터치/게임패드 → 조준점 계산               1. 인자 타입 확인
  DigValidation(허용오차 0)로 미리 확인            2. 구역 소유·생존·삽 장착
  조준 링 표시                                   3. 토큰 버킷 속도 제한
  스윙: RemoteEvent 1회 ───── DigRequest ────▶  4. DigValidation(허용오차 +4)
  즉시: 스윙 애니메이션·먼지·파편·소리              5. DigGrid.dig (높이맵 갱신 + 모래 흘러내림)
                                               6. TerrainRenderer: 바뀐 칸 사각형만 WriteVoxels
  ◀──────── 지형 자동 복제 ─────────────────────   7. ArtifactService: 노출도 계산
  PlotWatcher ◀── 속성 복제(State/Progress) ───      Hidden → Glimpsed → Discovered
  HUD·마커·발견 연출
```

### 3.1 좌표와 높이맵 (`src/shared/DigGrid.luau`)
- 구역 = 16×16칸, 칸 하나 = 4×4스터드(지형 복셀과 동일). 구역 크기 64×64스터드.
- 각 칸의 값 = 기반암 위 모래 높이(0~20스터드). **높이는 내려가기만 합니다.**
- **모래 흘러내림(경사 규칙):** 옆 칸보다 4스터드(대각선 4√2) 넘게 높을 수 없습니다. 깊게 파면 깔때기 모양이 되어 걸어서 나올 수 있고, 모래다운 느낌이 납니다. 처리 순서와 무관하게 같은 결과가 나오도록 "내리기만 하는 완화" 방식으로 구현했습니다.
- **바닥(minHeights):** 구역 가장자리는 바깥 사막(파이지 않음)과의 경사 규칙 때문에 얕게만 파이고, 유물 받침대 밑 칸은 유물 바닥 높이 아래로 파이지 않습니다(유물이 공중에 뜨지 않음).

### 3.2 지형 쓰기 (`src/shared/TerrainVoxels.luau`, `src/server/Services/TerrainRenderer.luau`)
- 칸 하나 = 복셀 기둥 하나. 층별 점유율 = `clamp((높이 − 층 바닥) / 4, 0, 1)` → 표면 높이가 연속적으로 표현됩니다.
- 원래 표면에서 8스터드보다 깊은 층은 **Sandstone(진한 모래층)** 으로 써서, 깊이 팔수록 색이 바뀌는 지층 효과를 냅니다.
- 한 번 스윙할 때는 바뀐 칸들의 경계 사각형만 다시 씁니다(보통 3×3~6×6 기둥 × 6층).

### 3.3 유물 노출 (`src/server/Services/ArtifactService.luau`)
- 노출도 = 유물 주변 칸(받침대 + 여유 1스터드)마다 `(유물 꼭대기 − 모래 높이) / 유물 높이`의 평균.
- **Glimpsed:** 받침대 위 칸이 유물 꼭대기보다 0.4스터드 내려가거나, 주변 칸이 2스터드 내려가면 → 반짝임 연출 + 진행 바 표시.
- **Discovered:** 노출도 ≥ 0.8 → 남은 모래가 쓸려 내려가며(서버가 주변 칸을 유물 바닥까지 내림) 유물이 완전히 드러나고, 보석이 빛나며 발견 연출.
- 보상은 서버가 계산한 상태에서만 발생합니다(클라이언트는 진행도를 보고하지 않음).
- 상태는 유물별 `Configuration` 속성으로 복제 → 재접속·리스폰·늦은 입장에도 같은 상태.

### 3.4 네트워크 예산
- 클라이언트 → 서버: 스윙당 `RemoteEvent` 1회(Vector3 하나). 최대 1/쿨다운 = Lv1 초당 3.3회, Lv2 초당 4회.
- 서버 → 클라이언트: 지형 변경(엔진 복제) + 상태가 바뀔 때만 속성 갱신(진행도는 2% 단위).
- 별도의 "발굴 결과" 응답은 보내지 않습니다(효과는 클라이언트가 즉시 재생).

### 3.5 부정 요청 방어
| 공격 | 방어 |
|---|---|
| Vector3가 아닌 값, NaN/무한대 | 타입 검사, 유한·범위 검사 → `BadInput` |
| 다른 사람 구역/구역 밖 | 서버가 아는 본인 구역 경계로만 판정 → `OutsideZone` |
| 하늘이나 땅속 조준 | 모래층 높이 범위 확인 → `BadHeight` |
| 먼 곳 원격 발굴 | 캐릭터 위치 기준 도달 거리 + 지연 허용 4스터드 → `TooFar` / `TooHigh` |
| 연타·매크로 | 토큰 버킷(버스트 3, 충전 = 1 / (쿨다운×0.9)) → `RateLimited` |
| 삽 없이 발굴 | 장착 도구의 `DigTool` 속성 확인 |
| 보상 위조 | 노출도·발견 판정은 서버 높이맵에서만 계산 |
분당 거절 30회 이상이면 서버 출력에 경고를 남깁니다(PHASE 0에서는 추방하지 않음).

### 3.6 개인 발굴 구역
- 서버당 6개 슬롯(`GameConfig.Plots.SlotOrigins`), 입장 순서대로 배정. 나가면 원상 복구.
- 슬롯 수와 서버 최대 인원을 맞춰야 합니다(게임 설정에서 Max Players = 6 권장).

### 3.7 저장 준비 (PHASE 3에서 연결)
- `DigGrid.encode/decode`: 칸당 URL 안전 문자 1개(64단계, 약 0.32스터드 정밀도). 16×16 구역 = 256자.
- 아직 DataStore에는 연결하지 않았습니다(사양서 단계 계획상 PHASE 3).

## 4. 확장 포인트

| 다음 단계 | 바꾸는 곳 |
|---|---|
| 유물 B·C(석조 구조물, 신전) | `GameConfig.Artifacts`에 항목 추가 + `ArtifactFactory`(또는 `ServerStorage.ArtifactTemplates`에 모델 배치) |
| 도구 단계·보상 | `GameConfig.Tools`, 플레이어 속성 `ToolLevel`(서버만 변경) |
| 더 큰 구역 | `ZoneCells` 증가(칸당 비용 동일, 저장 문자열 길이 = 칸 수) |
| 저장 | `PlotService`에서 `DigGrid.encode` + 발견 목록 + 도구 단계를 `UpdateAsync`로 저장 |
| 고품질 모델 | `ServerStorage.ArtifactTemplates/<Id>` 모델이 있으면 자동 사용(포함된 스크립트는 자동 제거) |

## 5. 알려진 한계 / Studio에서 확인할 것

- **4스터드 해상도**: 매끄러운 지형 메싱이 이 해상도에서 충분히 "모래를 파는 느낌"을 주는지는 Studio 실행으로만 판단할 수 있습니다. 거칠다면 (a) 칸 크기는 유지하고 점유율 곡선을 조정, (b) 발굴 가장자리 시각 효과 추가, (c) PHASE 2에서 EditableMesh 시각 레이어 검토 순으로 대응합니다.
- **지형 반영 지연**: 지형은 서버가 쓰고 복제되므로 핑만큼(보통 50~150ms) 늦게 파입니다. 효과·소리는 즉시 재생해 체감 지연을 줄였습니다. 부족하면 본인 구역에 한해 클라이언트 예측 쓰기를 검토합니다(복제 덮어쓰기 동작 확인 필요).
- **스윙 애니메이션**: 기본 Animate 스크립트의 칼 휘두르기(`toolanim = "Slash"`)를 임시 사용합니다. 삽질 애니메이션은 PHASE 2에서 제작이 필요합니다.
